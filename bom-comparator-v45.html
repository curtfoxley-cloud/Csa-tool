02 — Configuration Coverage Metrics
⚠ Work Order Status rule active: ABOM reconciliation requires quantity match AND Work Order Status = "CLOSED". Parts with open/missing WO status are counted separately below.
EBOM Build Status
ⓘ
The percentage of active EBOM line items traceable directly to a closed work order in the ABOM. This is the most conservative, audit-defensible build completion number — only exact PN+NH matches with a confirmed closed WO are counted.
Dev / Logic
Numerator: rMetric items where overall === 'ok' || 'flex_ok' (ok_m).
Denominator: metricTotal — rActive minus nh_match and collector items.
Formula: Math.round(ok_m / metricTotal * 100) + '%'.
—
EBOM Line Item Direct Trace to Closed WO
Exact PN+NH in ABOM, WO closed ÷ active scope
ⓘ
The percentage of active EBOM items covered by any form of embodiment — direct line-item, embodied as a Used On parent assembly, or via a reconciled indenture ancestor. A broader, program-realistic build picture.
Dev / Logic
Numerator: ok + nhMatchCnt + coveredCnt.
Denominator: activeTotal − collectorCnt (embDenominator).
Formula: Math.round(embNumerator / embDenominator * 100) + '%'.
—
EBOM Embodiment Coverage
Direct + used on embodied + parent indenture embodied ÷ active scope
ⓘ
Total number of rows in the uploaded EBOM file, including all part types — Collectors, References, Bulk Matl, and all active parts. No filtering applied.
Dev / Logic
r.length — raw result set length after runComparison().
Includes pt_collector, pt_reference, pt_bulk overalls.
Not used as a denominator for any issue metric.

EBOM Line Items
All items in engineering BOM
ⓘ
Active EBOM items after excluding Part Type = COLLECTOR, REFERENCE, and BULK MATL. This is the reconciliation scope used as the denominator for all issue and coverage metrics.
Dev / Logic
total − ptExcluded.
ptExcluded: results where overall === 'pt_collector' || 'pt_reference' || 'pt_bulk'.
Driven by EBOM col Z (COL.ebom.partType, index 25).

as_ = 'ok' when: abomMap key found, aq >= eq, woStatus === 'closed'.

ⓘ
Each bar shows the count of unique Work Order numbers from the ABOM file that carry that status. A single WO number may appear on many ABOM line items (one per part it covers), but is counted only once here. The status shown for each WO is taken from its first appearance in the ABOM file. When RFV data is loaded, non-Closed bars are split: the teal portion shows WOs with an RFV authorization; the remaining bar shows bare open WOs.
Dev / Logic
Source: buildWoRollup(abomData, COL.abom.woNo, COL.abom.woStatus).

NCR by Cause Code
ⓘ
Each bar shows the count of NCR disposition entries matched to EBOM items, grouped by Cause Code. One NCR Number may have many Disposition rows — each disposition row is counted separately (not by unique NCR Number). Cancelled NCR entries are excluded. An entry that qualifies under both Pool 1 (discrepant part match) and Pool 2 (originating WO match) may be counted up to twice. Top 6 cause codes shown.
Dev / Logic
Source: ncrEntriesPool1.concat(ncrEntriesPool2) across all result rows — no deduplication between pools.
Filter: (ncrStatus || '').toUpperCase() !== 'CANCELLED'.
Groups by: causeCode + ': ' + causeCodeDesc (or 'UNSPECIFIED' when blank).
Pool 1 = matched via NCR discrepantPart; Pool 2 = matched via NCR originatingWo → ABOM usedOn.
Counts are entry-level, not NCR-number-level. To count by unique NCR#, dedup on ncrNum.

Cancelled NCRs are excluded.
Dev / Logic
Source: ncrEntriesPool1.concat(ncrEntriesPool2) across all result rows.
Filter: ncrStatus !== 'CANCELLED' AND dispStatus must be non-blank.
Groups by: dispStatus raw string (case-sensitive from source data).
Semantic colors: CLOSED=green (#3fb950), WORKING=amber (#d29922), REVIEW=yellow (#e3b341), other=purple.
Top 6 statuses shown.
⚑   SME ADJUDICATION REQUIRED   ⚑
ⓘ
NCR rows whose discrepant part number appears in the CI input file, but whose originating work order does not trace back to a CI-anchored ABOM context through any of the three established CI trace paths (direct PN+NH, CI as Used-On, or ancestor indenture). This view does NOT assert that the discrepant part is a Configuration Item. A CSA subject matter expert must review each entry to determine whether the discrepant part is acting as a CI in the context of that work order. Counts all dispositions regardless of status; CANCELLED NCRs are excluded.
Dev / Logic
Source: computeCiCandidateNcrs() — standalone function, called from renderKpiBlocks().
Step 1: NCR discrepantPart in ciPnSet (CI file PN index).
Step 2 Exclusion — skip if ANY of:
  Path 1: abomWoToUsedOns[origWo].has(ciNh) — CI NH as used-on for this WO.
  Path 2: abomWoToUsedOns[origWo].has(ciPn) — CI PN as used-on for this WO.
  Path 3: abomWoToUsedOns[origWo].has(coveredAncestorPn) — ancestor covers this WO.
WO context type: Type A = WO absent from ABOM; Type B = WO in ABOM, context unanchored.
Stored in _kpiData.ciAdjudicationNcrs[]. Not surfaced in Summary table or filter bar.

NCR — CI Adjudication Required
NCRs with CI-file PN match, WO trace unanchored
ⓘ
EBOM items with ms=missing that have at least one structurally similar (near-match) unclaimed MBOM row. Near-match means the EBOM part number is similar to an unclaimed MBOM part number (Pool 1), similar to an unclaimed MBOM used-on value (Pool 2), or an ancestor of the missing EBOM item near-matches an unclaimed MBOM row (Pool 3). This does NOT change any reconciliation status — it is a separate investigative signal. A CSA SME should review this alongside the Missing in MBOM card. Phantom assembly nodes (EBOM intermediate design nodes not intended for physical build) typically generate no candidates and will not appear here. Near-match candidates that do appear warrant human review regardless of whether the EBOM item is a phantom. Items are grouped by EBOM anchor with cascade descendants listed beneath. Computed by Worker 2 after reconciliation completes.
Dev / Logic
Worker 2 (createNearMatchWorker) — runs after Worker 1 results posted.
Unclaimed MBOM rows: raw MBOM rows not in claimedDirect (inMbomDirectPool) or claimedUsedOn (inMbomUsedOnPool) sets reconstructed from state.results.
Candidate EBOM: results where ms === "missing" AND overall not pt_collector/pt_reference/pt_bulk.
Pool 1: EBOM PN vs unclaimed MBOM PN (prefix index, first 6 chars).
Pool 2: EBOM PN vs unclaimed MBOM used-on value (prefix index, first 6 chars).
Pool 3: Walk 6 ancestor levels via ebomPnToNh; check each ancestor vs unclaimed MBOM PNs.
Tier 1: Dash suffix variant (same base, different suffix). Tier 2: edit dist <= 3, 6-char prefix match. Tier 3: 7-char prefix match, edit dist 4-6.
Cascade: walk nhToChildren from each anchor; flag missing descendants as cascade children.
KPI count = unique EBOM PNs with at least one near-match hit across any pool.

CIs Embodied via Higher Parents
CIs covered by reconciled ancestor in MBOM/ABOM
ⓘ
Counts CIs whose exact Part Number + Next Higher Part Number combination appears directly in the RFV file. This is the most precise form of variance authorization — the RFV was written explicitly against that part in that assembly context, not just against a work order or an NCR. A high count here indicates well-documented, part-specific variance coverage.
Dev / Logic
For each CI row (CI file col B = pn, col C = nh): look up pn + '||' + nh in rfvByPnNh map.
rfvByPnNh built from RFV file col B (pn) + col C (nh), independent of pass waterfall.
Match is exact after normPN() — case-insensitive, whitespace-stripped.
A CI may match multiple RFV rows; all are shown in the drill-down.
Computed in renderKpiBlocks() → rfvP1CIs array.

CIs with Direct RFV (P1)
CI PN+NH matched directly to RFV Part Number+NH
ⓘ
Counts CIs that are linked to an RFV through the quality chain: the CI is connected to an NCR (because it appears as the NCR's discrepant part or as a Used On assembly for the NCR's originating work order), and that NCR's Disposition Number appears in the RFV file. This KPI checks ALL NCR dispositions regardless of status — open, closed, or blank — because an RFV can exist against a disposition that has since been closed. This is intentionally different from the "CIs with Open NCR Dispositions" KPI, which only counts open (non-closed) dispositions. A CI that appears here but not in the open NCR KPI means its NCR was dispositioned and closed — often because the RFV formally authorized the variance and the NCR was resolved. A CI appearing in both means an open NCR AND a matching RFV exist simultaneously. Requires the NCR file to be loaded.
Dev / Logic
Step 1 — CI → NCR join (all dispositions, not just open):
  Path A: NCR discrepant part = CI pn AND ABOM used-on for NCR origWo includes CI nh.
  Path B: CI pn appears in ABOM used-on values for the NCR's originating WO.
Both paths anchored to ABOM WO context via abomWoToUsedOns lookup.
Step 2 — NCR dispNo → RFV join:
  Collect all dispNo values from matched NCR rows → ciKeyToNcrDispNos.
  Check each dispNo against rfvByDispNo (built from RFV col F).
Computed in renderKpiBlocks() → rfvP2CIs array. Dims if NCR file not loaded.
—
CIs with RFV via NCR Disp (P2)
CI linked to an NCR whose Disp# is covered by an RFV
ⓘ
Counts CIs that are linked to an RFV through the work order chain via three possible geometries. Geometry A: the CI's PN+NH combination appears directly in ABOM as a component (Pool 1). Geometry B: the CI's PN appears as the next-higher assembly (usedOn) in ABOM, meaning the CI is the assembly and other parts are built under it on that WO (Pool 2). Geometry C: the CI is not directly in ABOM but is covered by a reconciled ancestor PN found via indenture tree walk, and that ancestor's WO appears in the RFV file (Pool 3). In all cases the WO number on the ABOM row must match a WO number in the RFV file. The drill-down shows which geometry applies to each link.
Dev / Logic
Three ABOM WO maps built simultaneously:
  abomKeyToWos: "pn||usedOn" → WO Set (Geometry A — component lookup)
  abomUoToWos: "usedOn" → WO Set (Geometry B — assembly lookup)
  abomAncestorPnToWos: "pn" and "usedOn" → WO Set (Geometry C — ancestor lookup)
For each CI: collect WOs from all three maps, deduplicate by rfvNum+WO pair.
Geometry C: uses result.coveredAncestorPn from the comparison run (overall='covered').
Each RFV entry tagged with geometry A/B/C and geometryLabel for drill-down display.
Computed in renderKpiBlocks() → rfvP3CIs array.

CIs with RFV via Work Order (P3)
CI has an ABOM WO# that appears in the RFV file
ⓘ
The total count of unique CIs that have at least one RFV link via any of the three match passes — direct PN+NH (P1), NCR Disposition (P2), or Work Order (P3). A CI is counted once even if it appears in multiple passes. This is the broadest coverage metric and represents the total number of CIs for which some form of formal variance authorization exists in the system.
Dev / Logic
Union of rfvP1CIs + rfvP2CIs + rfvP3CIs, deduplicated by CI identity key (ciId || pn).
coveredCiKeys Set tracks unique identities across all three pass loops.
rfvAnyCIs built in a second pass over CI file: include row if its key is in coveredCiKeys.
passFlags object records which passes (p1/p2/p3) apply per CI for the drill-down matrix.
Computed in renderKpiBlocks() → rfvAnyCIs array.

CIs with Any RFV Coverage
CIs linked to at least one RFV via any pass
ⓘ
The highest-priority audit closure metric: CIs that have an unresolved reconciliation discrepancy (Missing, WO Not Closed, Qty Mismatch, or Parentage Mismatch) AND have no RFV coverage through any of the three passes. These are the items most likely to require corrective action or additional documentation before a CSA can be formally closed. A count of zero here indicates all open CI discrepancies are at least covered by an existing variance authorization.
Dev / Logic
Filter: CI not in coveredCiKeys (no P1/P2/P3 RFV link) AND result.overall is in
openIssueStatuses = { 'missing', 'wo_open', 'qty_mismatch', 'nh_mismatch' }.
result looked up via resultByKey Map (pn + '||' + nh key from comparison run).
Does NOT include 'proc_removed' or 'covered'/'nh_match' (embodiment statuses).
Block dims to 50% opacity when count = 0. Computed → rfvNoneCIs array.

CIs — Open Issues, No RFV
CIs with unresolved discrepancies and no RFV coverage
ⓘ
Counts how many CI rows have a matching Authorization Clearance Notice (ACN), out of all CI rows loaded. The join is: CI Part Number = ACN Part Number. Because ACNs are part-number-based while CIs are defined by a Part Number + Next Higher Part Number combination, a single ACN can authorize multiple CI rows. CI rows are therefore not deduplicated — each CI row is evaluated individually. Click to see which CIs trace to an ACN and which do not.
Dev / Logic
Source: renderKpiBlocks() → ciAcnLinked / ciAcnUnlinked arrays.
Step 1 — Build acnByPn Map: normPN(ACN Part Number, Col C) → [{recNo, recRev, pn, level}].
Step 2 — For each CI row: normPN(CI PN) lookup in acnByPn.
  Hit → push to ciAcnLinked (row carries all matching ACN records).
  Miss → push to ciAcnUnlinked.
Numerator = ciAcnLinked.length · Denominator = total CI rows (no dedup by PN).
Stored in _kpiData.ciAcnLinked / _kpiData.ciAcnUnlinked.
